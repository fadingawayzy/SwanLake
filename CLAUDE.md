# SwanLake — Memory file for AI development agents

Этот файл читают все ИИ-агенты при старте работы над проектом.
При работе с этим репозиторием **ОБЯЗАТЕЛЬНО** следуй правилам ниже.

> Файл `AGENTS.md` — символическая копия этого файла; правь только
> `CLAUDE.md`.

## Правила работы (Cardinal Rules)

### Rule 1 — Plan First, Code Once (Waterfall)

Для любой нетривиальной задачи (>20 строк изменений) сначала
**ОБЯЗАТЕЛЬНО**:

1. Включи Plan Mode.
2. Прочитай `ARCHITECTURE.md` целиком.
3. Прочитай задействованные модули целиком.
4. Сгенерируй план с явной структурой:
   - Какие `BLOCK_ID` будут затронуты.
   - Какие новые `BLOCK_ID` будут созданы (с предложением имён).
   - Какие контракты модулей изменятся.
   - Какие инварианты могут пострадать.
5. Согласуй план с человеком.
6. **Только после согласования** — переходи к коду.

Не итерируй «правка → тест → правка». Этот стиль создаёт технодолг.

---

### Rule 2 — GRACE Anchors

Каждый функциональный блок в `.py` файлах обрамляется:

```python
# === START_<BLOCK_ID> ===
def some_function():
    ...
# === END_<BLOCK_ID> ===
```

`BLOCK_ID`:

- `UPPER_SNAKE_CASE`
- уникален во всём проекте (см. `ARCHITECTURE.md` → раздел `<modules>`)
- начинается с глагола действия (`LOAD_`, `BUILD_`, `PARSE_`,
  `NORMALIZE_`, ...)

При добавлении нового блока — сначала **зарегистрируй `BLOCK_ID`** в
`ARCHITECTURE.md`, затем пиши код.

---

### Rule 3 — Diff Rules (только через якоря)

При любой правке кода используй `apply_diff` (Kilo Code) или Edit tool
(Claude Code) с такими свойствами:

- **SEARCH-блок ОБЯЗАН** содержать `# === START_<BLOCK_ID> ===` в
  первой значащей строке и `# === END_<BLOCK_ID> ===` в последней.
- **REPLACE-блок ОБЯЗАН** тоже содержать те же якоря.
- Это гарантирует атомарность и предотвращает катастрофическое
  частичное замещение, если поисковая фраза неоднозначна.
- **НЕ ПОЛАГАЙСЯ** на номера строк из своих «предположений».
  Positional Encoding в LLM плохо работает с ними. Получай номера
  строк **ТОЛЬКО** через `read_file`/`view`, не угадывай.

---

### Rule 4 — Cross-Model Verification

Никогда не проси одну и ту же модель и сгенерировать решение, и его
проверить (RLHF-сикофантия, см. arXiv:2503.23674).

Этот принцип уже встроен в продукт (`generator.py` vs `verifier.py` —
разные модели через `OPENROUTER_MODEL` и `OPENROUTER_VERIFIER_MODEL`).

Тот же принцип распространяется на разработку: если код писал Sonnet,
ревью делает Gemini или DeepSeek. Не стесняйся переключать модель.

---

### Rule 5 — Don't Add Heavy Tests

Для проекта SwanLake (~5000 строк) не нужны `pytest`/`unittest` суиты.
Mental execution LLM на 100-200 строк надёжен на 99%
(см. arXiv:2403.15852).

Логика валидируется через:

- `coverage.py` (КЭС × файлы)
- `seed_demo.py` (smoke test)
- `verifier.py` (cross-model на самих задачах)

Если хочется тестов — пиши их как `tests/benchmark.py` с фиксированным
датасетом из `data/` + автосравнением через `verifier.py` логику.
**Не пиши mocks/fixtures для unittest.**

---

### Rule 6 — Frontmatter Discipline

В сгенерированных `vault/<subject>/<kes>/*.md`:
ю
- `kes_code`: **ВСЕГДА** строка в кавычках (`"2.10"`, не `2.10`)
- `task_number`: **ВСЕГДА** строка в кавычках
- `source_id`: **ВСЕГДА** строка
- `date`: ISO 8601 (`YYYY-MM-DD`)
- `status` ∈ `{"new", "pass", "fail", "partial"}`

---

### Rule 7 — JSON-free Long Context

Для длинных промптов LLM (>4000 токенов контекста) — **НЕ используй
JSON** для структурирования (см. OpenAI GPT-4.1 Prompting Guide).
Используй **Markdown + XML-теги**. JSON оставь для БД/API/`.json`
файлов на диске.

---

### Rule 8 
- Если переменная/словарь определены дважды (один раз внутри якорей,
  один раз снаружи) — это баг агента. Удалить дубль снаружи якорей.

## Часто задаваемые задачи

### Добавить новую модель LLM

1. Прочитай `llm.py:GET_PRIMARY_MODEL` и `llm.py:GET_VERIFIER_MODEL`.
2. Обнови `.env.example`.
3. Никаких изменений в коде — модели читаются из env.

### Добавить новый предмет (например, химия)

1. Архитектурный план в Plan Mode.
2. Расширить `modification_framework.json` → `subjects`.
3. Добавить `scraper.py:SCRAPE_<SUBJECT>` блок.
4. Зарегистрировать в `SUBJECT_RU` mapping в `generator.py`.
5. `data/<subject>.json` должен появиться через `scraper.py`.
6. Запустить `coverage.py` — должен показать 0 missing.

### Найти в коде функциональный блок

Не используй grep по строкам кода — используй grep по
`START_<NAME>`. Якоря уникальны — найдёшь ровно один результат.

### Кросс-проверить чужую правку

Если код менял Sonnet, запусти ревью на Gemini 3 Pro / DeepSeek с
промптом:

> «Прочитай diff и проверь на: (а) сохранение всех инвариантов
> из `ARCHITECTURE.md` § 6, (б) совпадение пар START/END якорей,
> (в) отсутствие JSON в промптах для long context.»

## Цена за нарушения

- **Нарушил Rule 1** (планирование): через 3-5 итераций накопится
  технодолг. Возврат стоимости — рефакторинг ≥ 1 дня работы.
- **Нарушил Rule 2/3** (якоря в diff): риск повредить код через
  replace без возможности заметить (см. статистику Cline: ChatGPT
  8% битых патчей, даже Claude — 2%).
- **Нарушил Rule 4** (cross-model): сикофантия RLHF будет одобрять
  решения, которые твоя же модель генерирует. Качество
  замаскированно деградирует.
- **Нарушил Rule 5** (heavy tests): тесты сами станут семантическим
  шумом, и LLM начнёт «оптимизировать под тесты» — потеря
  обобщения.
